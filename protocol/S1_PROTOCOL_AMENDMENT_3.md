## What changes

1. **Primary rater (fixes the rater named under Amendment 1 item 1).** The S1 primary rater is one Devin built-in agent workflow. The vendor routes its requests to backend models that it does not disclose, and the routing may differ between requests. The rater is therefore the workflow, not a named model: its backend models, versions, decoding settings and per-request routing are not known. The run log and the paper record it as "Devin built-in agent workflow, backend routing undisclosed by vendor", with the Devin mode name and the first and last run dates. No other workflow or model labels any pair.
2. **Run record (replaces, for this rater, the record of Amendment 1 "What stays the same" bullet 3).** The 844 pairs run in the frozen 96 packet batches. The following are stored, and nothing more:
   - Private custody (D5): the packet batches, the exact prompt bytes submitted to the workflow for each batch, each raw response as returned, the sealed primary output (the 844 primary labels parsed from the sealed raw responses), and the batch log.
   - The batch log has one record per attempt: batch index, packet batch-manifest SHA-256, SHA-256 of the submitted prompt bytes, SHA-256 of the raw response, attempt status, Devin session ID and timestamp.
   - Runner bundle and receipts: the packet hash, the sealed primary-output hash and the batch-log hash. Per §10 the per-pair S1 labels enter the committed ledger. No prompt, response or packet content is committed.
   - Not stored, because it is not visible to the study: any instructions or context the vendor adds, the backend model and routing of each request, and the input the backend model actually received. The vendor's own retention of session content follows the plan's terms and is outside this protocol.
   - A batch whose response is schema-valid is sealed and never run again. A batch that fails (no schema-valid response, or a session failure) is rerun from the last sealed batch with the same prompt bytes. Every failed attempt keeps its log record and stored response, and none of its labels is used.
3. **Blind author check (new, descriptive only).** The author labels a fixed sample of 50 of the 844 desk-rateable pairs.
   - Draw rule: for each desk-rateable pair, compute SHA-256 of the compact UTF-8 JSON `["eapg-s1-author-check-v1", 20261123, corpus, pair_id]` (separators `,` and `:`, `ensure_ascii=False`). Sort ascending by that hash, with lexical ties on `corpus:pair_id`. Take the first 50. The seed is 20261123. The draw is committed with its SHA-256 before any production label exists.
   - Blinding: the author uses the same packet material, rubric and closed label set as the rater. The author sees no model label for any pair, including the pilot labels, and no S2 or S3 result. The author's 50 labels are hash-sealed before the author sees any production label. If the author has seen a model label for a sampled pair, that pair stays in the sample and is reported as unblinded.
   - Statistic: raw percent agreement and Cohen's κ between the primary rater and the author on the 50 pairs, on exact labels and on bucket labels (pass, source, contract, route), with counts. The 95% interval for κ is the whole-cluster percentile bootstrap of §4 (clusters sorted ascending, Python `random` seed 42, 10,000 draws, nearest ranks 250 and 9,750). Pairs in the sample can share a cluster, so this is a descriptive interval.
   - Status: this is a descriptive reliability check. It is not a secondary outcome, it does not restore S11, and it is never part of the Holm family. Disagreements are reported only. They never change a primary label, and nobody adjudicates them.
4. **Runner evidence contract (extends Amendment 2 item 5).** For a bundle run under this amendment, the S1 evidence is the packet hash, the sealed primary-output hash and the sealed batch-log hash of item 2. A private verifier with custody recomputes the seal and batch-log hashes from the stored files and checks that every `desk` entry in the bundle equals the sealed primary label for its pair; a bundle that fails either check is refused. Author-check labels are never S1 evidence, and the runner must refuse a bundle that offers them, a second-rater pin or an agreement-draw pin in that role. The checkpoint header records this amendment's SHA-256 and a design label distinct from `amendment_1` and the Amendment 2 label.
5. **Production hold.** Committing or merging this amendment does not start or authorize production labeling. Production S1 labeling starts only on a separate, dated owner authorization recorded in the run log. Until then, no production label is produced.

## Reason

The S1 budget is $0. The unpaid Gemini API conflicts with packet custody, as recorded in Amendment 2. An open-weights model in a free Colab session was also weighed. It is not practical as the primary rater, because free GPU sessions are capped and preemptible, each one needs the owner to start it, and its quality on this rubric is untested. The Devin workflow runs inside the existing plan at no additional cost and keeps packets in the custody already used for the pilot. The blind author check is added so that reliability is checked independently of the model. No threshold, outcome or test changes. The change is procedural.

## Deviations from the frozen protocol and owner rules

1. §2 line 54 and ground rule R7: the S1 labels come from a workflow whose backend models, versions, decoding settings and routing are not disclosed. The disclosure is the workflow name, mode, run dates, session IDs, and the hashes of the submitted prompts and raw responses.
2. Amendment 1 "What stays the same" bullet 3 and Amendment 2 "What stays the same" bullet 5: the rater record holds no model ID, version or decoding settings, and the stored prompt is the submitted prompt, not the full input the backend model received, because the vendor exposes neither.
3. Owner rule D4 (no human raters) and the repository skill `eapg-blind-validation`: a human author labels 50 pairs as a descriptive check, by owner decision on 2026-11-23. The S1 labels themselves remain model labels.
4. Owner rule D5 (private files never enter a chat message or an external service): the private S1 packets are processed in Devin custody for primary labeling. Devin's built-in workflow receives the packet contents and returns the raw responses. No other service receives them, and the packets, prompts and raw responses are never committed or published. This was decided by the owner on 2026-11-23.
5. §11: a change needs "disjoint evidence". There is none for a budget and custody constraint. The decision and its reason are recorded here instead.

## Effect on claims

- The S1 labels are a recorded measurement from one workflow with undisclosed backend routing, not a reproducible rater. Nobody can rerun the labels. P1–P3 computed from them are therefore `replay-only`, never `re-executable`.
- Verification with custody: a private verifier recomputes the seal and batch-log hashes from the stored prompts, responses and labels, and checks every `desk` entry against the sealed primary labels.
- Verification without custody: an external reviewer can check that the runner and receipts pin the committed hashes, and can replay everything from the committed per-pair labels onward. The reviewer cannot see prompts or responses, so cannot check them against their hashes. Nobody can check what the backend model received.
- The paper calls the S1 labels model-based labels from one Devin workflow with undisclosed backend routing, and calls the 50-pair comparison a blind author check on a fixed sample. It never calls it human validation, expert labels or ground truth, and never extends it to all 844 labels.
- §12 replaces Amendment 2's line "S1 labels come from one model. No second model or human checked them." with: "S1 labels come from one Devin workflow whose backend routing the vendor does not disclose, so they cannot be reproduced. No second model checked them. The author checked a fixed blind sample of 50 pairs; that agreement is descriptive only."
- §12 "Desk labels are model-based, not human" still holds for every S1 label.
- Which backend models produced which labels is not known. The paper reports the run dates and session IDs and makes no claim that one model or model version produced every label.
